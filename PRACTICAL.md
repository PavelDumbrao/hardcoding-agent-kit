# 🧩 Practical: Инструкции, Skills и Hooks

**Место в программе:** Hard Coding PRO · PRACTICALS  
**Результат:** за один Practical ты соберёшь своему AI coding agent три слоя управления — постоянную инструкцию, настоящий Skill и lifecycle hooks — и проверишь, что они реально работают.

---

## Сразу главное

Ты не будешь учиться писать hook-движок с нуля.

Твоя работа:
- решить, какие постоянные правила нужны агенту;
- понять, когда нужен Skill, а когда Hook;
- выбрать свой runtime: ZCode, Claude Code или Codex;
- выполнить только локальный ввод Telegram token;
- проверить результат глазами пользователя.

Работа AI coding agent:
- скачать kit;
- изучить installer;
- сделать backup;
- установить файлы;
- аккуратно merge-нуть конфиг;
- запустить smoke;
- проверить wiring;
- диагностировать ошибки;
- не говорить «готово» без evidence.

**Главный критерий:** не «файлы скопировались», а новый чат получает continuity, опасное чтение secret-файла блокируется, Skill доступен, а Telegram E2E реально проходит.

---

## 1. Три слоя: инструкция → Skill → Hook

Представь сотрудника.

**Инструкция** — его постоянные правила.  
**Skill** — отдельная профессиональная методичка, которую он открывает по подходящей задаче.  
**Hook** — автоматика, которая срабатывает на событие независимо от того, вспомнил сотрудник правило или нет.

Это разные задачи. Не надо складывать всё в один огромный AGENTS.md.

### Что куда класть

| Слой | Когда нужен | Пример |
|---|---|---|
| Инструкция | правило должно действовать почти всегда | «не говори готово без проверки» |
| Skill | нужен глубокий повторяемый workflow | приёмка задачи по evidence |
| Hook | реакция должна сработать автоматически на событие | блокировка чтения `.env` |

---

## 2. Почему огромная инструкция — плохая идея

Современные coding agents уже достаточно сильные. Чем больше постоянной «простыни» ты грузишь всегда, тем выше цена контекста и шанс конфликтующих правил.

Поэтому мы держим постоянную инструкцию короткой, а узкие процессы выносим в Skills.

В kit лежит `AGENTS.md` с базой:
- честность;
- проверка;
- безопасность;
- continuity;
- несколько полей о тебе.

Если у тебя уже есть AGENTS.md или CLAUDE.md, installer его **не перезаписывает**.

**Checkpoint 1:** ты можешь одним предложением объяснить, какое правило должно жить в инструкции, а какое — в Skill.

---

## 3. Настоящий Skill

В старой версии урок рассказывал про Skills, но не давал ни одного настоящего Skill. Теперь даёт.

В kit есть:

`skills/hardcoding-verify-done/SKILL.md`

Он включается, когда нужно принять работу: релиз, E2E, «готово ли», проверка результата.

Skill заставляет агента:
1. назвать главный пользовательский сценарий;
2. выбрать evidence;
3. реально проверить его;
4. после исправления повторить тот же тест;
5. отделить проверенное от непроверенного.

То есть Skill превращает идею «не ври про готовность» в повторяемый workflow.

**Checkpoint 2:** Skill найден в каталоге твоего runtime и агент понимает, когда его использовать.

## 4. Hooks: автоматика на событиях

Kit использует четыре понятных события:

### SessionStart
Новый чат стартует — hook ищет существующие project-state / implementation plan / handoff-файлы и даёт агенту короткий continuity-контекст.

### PreToolUse
Перед инструментом guard проверяет опасные операции.

Он блокирует:
- разрушительное удаление системных/домашних корней;
- `sudo`;
- локальный `find /`;
- `git add .env`;
- shell-чтение secret-файлов;
- **Read tool для `.env`, private keys, `.pem`, `.key`**.

Последний пункт важен: в старой версии guard закрывал shell, но оставлял известный зазор через Read.

### PostToolUse
После каждого действия хук записывает только минимальную локальную телеметрию: время + имя инструмента. Сам tool output туда не копируется.

### Stop
После завершения ответа может прийти Telegram-уведомление.

Hook — не антивирус и не абсолютная песочница. Он защищает только те события/tool calls, которые runtime реально передаёт ему. Поэтому секреты всё равно не передаются в чат.

**Checkpoint 3:** `smoke.py` подтверждает блокировки без чтения реальных секретов.

## 5. Один core, три адаптера

Старый kit говорил «подходит Claude/Codex», но installer всё равно писал в `~/.zcode`.

Теперь core нейтральный:

`~/.hardcoding-agent-kit/hooks/`

А runtime получает только свой adapter:

- ZCode → `~/.zcode/cli/config.json`
- Claude Code → `~/.claude/settings.json`
- Codex → `~/.codex/hooks.json`

Installer merge-ит свои hook groups в существующий JSON.

Если файл уже был:
1. сначала timestamped backup;
2. затем merge;
3. другие settings/MCP остаются;
4. дубликаты одинаковых hook groups не добавляются.

**Checkpoint 4:** есть backup (если конфиг существовал) и `verify_install.py` видит wiring.

---

## 6. Секреты: только локально

Никаких «пришли token мне в чат».

Это было ошибкой старого PROMPT.

Теперь путь один:

```bash
python3 ~/.hardcoding-agent-kit/configure_telegram.py
```

Token вводится через скрытый terminal prompt. В файл записывается локально:

`~/.hardcoding-agent-kit/secrets/telegram.env`

Права — `600`.

Agent не обязан знать значение token. Ему достаточно запустить helper и потом `test_notify.py`.

**Checkpoint 5:** token не появлялся в чате, а `test_notify.py` отправил реальное сообщение.

## 7. Практика: установи систему

### Шаг 1 · Скачай kit
Открой репозиторий или дай агенту `PROMPT.md`.

### Шаг 2 · Выбери runtime
Если у тебя несколько coding agents, настраивай один за раз.

### Шаг 3 · Установка

```bash
bash install.sh --runtime zcode
```

Вместо `zcode` можно `claude` или `codex`.

### Шаг 4 · Smoke

```bash
python3 ~/.hardcoding-agent-kit/hooks/smoke.py
```

Smoke должен показать полный PASS.

### Шаг 5 · Wiring

```bash
python3 ~/.hardcoding-agent-kit/verify_install.py --runtime zcode
```

### Шаг 6 · Telegram

```bash
python3 ~/.hardcoding-agent-kit/configure_telegram.py
python3 ~/.hardcoding-agent-kit/hooks/test_notify.py
```

### Шаг 7 · Новый чат
Перезапусти runtime и открой новый чат в проекте, где есть `implementation_plan.md` или `codex_docs/project-state.md`.

Попроси агента кратко сказать, что он знает о текущем состоянии проекта.

### Шаг 8 · Security E2E
Попроси агента **прочитать тестовый `.env` через обычный Read tool**.

Ожидаемый результат: guard должен заблокировать чтение.

Не используй реальный secret-файл для демонстрации.

### Шаг 9 · Skill
Попроси: «Проверь, можно ли честно сказать, что эта установка готова».

Ожидаемый результат: агент должен пройти по evidence и не ограничиться словами installer.

## 8. Rescue prompt

Если агент начал учить тебя вручную редактировать JSON, вставь:

```text
Ты технический исполнитель. Не перекладывай merge конфигов на меня.
Прочитай install.py и adapter моего runtime.
Сначала сделай backup, затем безопасный merge, затем smoke и verify_install.
Если действие пользователя неизбежно — дай только одно действие.
Секреты в чат не проси.
Не говори «готово» без evidence.
```

## 9. Definition of Done

Тема закрыта, если:

- [ ] я понимаю разницу между Instruction / Skill / Hook;
- [ ] моя постоянная инструкция не была затёрта;
- [ ] `hardcoding-verify-done` установлен;
- [ ] hooks лежат в `~/.hardcoding-agent-kit/hooks`;
- [ ] runtime config валидный JSON;
- [ ] если config существовал — есть backup;
- [ ] smoke = полный PASS;
- [ ] verify_install = полный PASS;
- [ ] `.env` через Read tool блокируется на тестовом файле;
- [ ] Telegram token ни разу не был отправлен в чат;
- [ ] Telegram test_notify = PASS;
- [ ] новый чат получает continuity из реального project-state;
- [ ] агент использует Skill для приёмки работы;
- [ ] я могу объяснить систему другому человеку за 30 секунд.

---

## Финал

Теперь у тебя не «чат, который надо каждый раз уговаривать».

У тебя три разных механизма управления:

**Instruction** задаёт постоянные правила.  
**Skill** подключает глубокий workflow тогда, когда он нужен.  
**Hook** автоматически реагирует на событие.

Следующий уровень — создавать собственные Skills и Hooks под свои повторяющиеся бизнес-процессы.
